# 하이스케치 PoC — 평가 결과

| 항목 | 내용 |
|---|---|
| 문서 상태 | **평가 실행 완료 (규칙 기반 변환기)**. 외부 LLM 미사용 방침 확정 — 이 변환기가 최종 산출 경로 |
| 실행일 | 2026-09-10 |
| 실행 조건 | `src/pipeline/deterministic.js` (규칙 기반 변환기)로 8개 케이스 + CONSIST 3회 실행 |
| 실행 도구 | `node scripts/run-eval.mjs` → `runs/<timestamp>/<CASE>/{payload,screen.xml,preview.html,report}.json` |
| 변환기 반영 | ① 읽기순 정렬 + `catalog/websquare/mapping.json` 매핑  ② 필수(＊) 라벨→인접 필드 전파  ③ `area` 자식 중첩 |
| 실행 환경 | 로컬 (`npm run dev`, Chrome 최신). 외부 공개 샘플만 사용(§9.2) |
| 관련 | 개발지시서 §8.4 T-6, §10 수락 기준, §1 성공 판정 |

> **성격**: 규칙 기반 변환기는 캔버스 배치를 **자연어 해석 없이** WebSquare 태그로 옮긴다.
> "note 규칙 반영·레이아웃 유형 인식·토큰 스타일" 은 하지 않으므로(§4.2 지시서), 아래 정성 점수는 그 한계를 반영한다.
> 개선 여지는 §6 후속 과제(A-3b) 로 관리한다.

산출물 위치: `runs/<timestamp>/` (gitignore — 로컬). 재현: `node scripts/run-eval.mjs`.

## 3. 화면별 정성 평가 (SC-1 — 사용 가능한 초안인가)

> O/△/X, 종합 4단계. 규칙 기반 변환기의 구조적 특성이 그대로 반영된 결과.

### 3.1 공통 관찰

| 항목 | 관찰 |
|---|---|
| 컴포넌트 매핑 | **정확**. `input→w2:inputBox`, `date→w2:calendar`, `select→w2:selectBox`+`<option>`, `list→w2:gridView`+`w2:gridColumn`, `text→w2:textarea`, `button→w2:trigger`, `label/title→w2:textbox`. 8케이스 미매핑 0 |
| 텍스트 정확도 | **완벽**. 라벨·컬럼명이 입력한 그대로(기계적 복사). E-QUERY 담당자 컬럼 추가도 정확 반영 |
| XML well-formed | **OK**. 8케이스 전부 태그 균형, `<w2:group id="screenRoot">` 래핑, Preview HTML 렌더 가능 |
| 결정성 | **완벽**. 동일 입력 → byte-identical |
| 레이아웃 정리 | **부분**. `area` 안의 요소가 `<w2:group>...</w2:group>` 자식으로 **중첩됨**(N-LIST 조회영역 1, N-FORM 섹션 2, N-MAIN 카드 3, N-DETAIL 2). 좌표는 Preview 에 보존. **단** 정렬(버튼 우측)·조회/결과 영역의 "유형" 인식·섹션 간 순서 규칙은 미적용 (§4.2 지시서: 하지 않음) |
| 필수(＊) 처리 | **반영됨**. 필수 라벨 → 같은 줄 오른쪽(없으면 바로 아래) 필드로 전파. N-FORM 3건(성명·구분·주민번호 → `w2input_essential`/`w2selectbox_essential`), N-LIST·N-DETAIL·N-BLANK 각 1건. `mapping.json` 의 `requiredClass` 로 출력 |
| 보충 설명(note) 반영 | **없음 (설계상)**. "주민번호 필수", "등록일 오늘 기본값" 등 자연어 규칙은 해석하지 않는다. note 는 payload 에 담겨 개발자에게 전달만 됨 |
| 미확정 처리 | **질문 안 함 (설계상)**. 애매해도 변환만 수행 |
| 표준 준수 | **부분**. raw `w2:*` 태그 + `requiredClass`. `componentKey`/`tokenKey` 추상화·토큰 스타일·버튼 역할색은 후속 과제(A-3b) |

| 케이스 | 레이아웃 | 컴포넌트 | 표준 준수 | 텍스트 | 미확정 | XML | 종합 | 코멘트 |
|---|:--:|:--:|:--:|:--:|:--:|:--:|:--:|---|
| N-LIST | △ | O | △ | O | X | O | **2~3** | 조회영역 area 가 조회조건을 감쌈, 계약번호 필수 전파. 버튼 활성화 조건·"조회영역/결과영역" 유형 인식은 없음 |
| N-DETAIL | △ | O | △ | O | X | O | **2** | 상단 목록/하단 상세 요소·area 2개 중첩. "행 선택→상세" 연동 없음(예상) |

**SC-1 판정**: 종합 대체로 **2~3** — N-FORM/N-BLANK 는 3("소폭 수정 후 사용"). "쓸 만한 골격"은 나오지만 정렬·유형 인식·표준 스타일은 사용자가 후수정해야 한다. 개선 여지는 §6.
- 화면 "유형" 패턴 인식 — 조회영역/결과영역, 카드/대시보드 레이아웃 규칙 (A-3b)
- `componentKey`/`tokenKey` + 토큰 스타일, 버튼 우측 정렬·역할색 (A-3b)
- `mode=edit` 시 baseScreen 대비 변경분만 해석 (선택)

## 4. 스타일 일관성 (SC-2 / AC-10)

CONSIST: N-LIST 동일 입력 3회 (`CONSIST/run1..3.xml`).

| 비교 항목 | 1회차 | 2회차 | 3회차 | 편차 평가 |
|---|---|---|---|---|
| 출력 XML | (기준) | 1회차와 동일 | 1회차와 동일 | **byte-identical** |
| 사용 태그 집합 | group·textbox·inputBox·trigger·calendar·gridView·gridColumn | 동일 | 동일 | 편차 0 |
| 그리드 컬럼 수/순서 | 5 (순번,계약번호,계약자,체결일,상태) | 동일 | 동일 | 편차 0 |
| 버튼 개수/문구/정렬 | 2 (조회, 초기화) | 동일 | 동일 | 편차 0 |

**SC-2 판정**: **충족**. 규칙 기반 변환기는 정의상 동일 입력 → 동일 출력(byte-identical). 흔들림 없음.

## 5. 시간 단축 (SC-3)

## 6. 종합 판단

| 성공 기준 | 결과 | 근거 |
|---|:--:|---|
| SC-1 사용 가능한 초안 | **부분 충족 (2~3)** | §3 — "쓸 만한 골격"은 나옴. 정렬·유형 스타일 후수정 필요 |
| SC-2 스타일 일관성 | **충족** | §4 — byte-identical |
| SC-3 시간 단축 | **긍정적** | §5 — 생성 지연 없음, 스케치가 수작업보다 빠름 |
| §10 수락 기준 | **AC-10 외 P/부분** | §2 |

**정식 개발 전환 판단**: 규칙 기반 변환기는 **"골격 자동 생성 + 사용자 후수정"** 모델로 실용 가능성 있음. 아래 후속 과제로 후수정 분량을 줄이면 SC-1 을 3 이상으로 끌어올릴 수 있다.

**후속 과제** (백엔드, A-3b):
- 화면 "유형" 패턴 인식 — 조회영역/결과영역, 카드/대시보드 레이아웃 규칙
- `componentKey`/`tokenKey` 추상화 + 토큰 스타일, 버튼 우측 정렬·역할색
- `mapping.json` `requiredClass` 명칭을 사내 WebSquare 표준으로 확정 (현재 관례적 추정값)
- `/api/generate` 시 `runs/` 자동 저장 (AC-10)
- `mode=edit` 시 baseScreen 대비 변경분만 해석 (선택)
