각 케이스는 에디터에서 **그대로 재현 가능하도록** 입력을 명시한다.

## 3. 화면별 정성 평가 (SC-1 — 사용 가능한 초안인가)

각 케이스 실행 후 아래 표를 채운다. 항목별 **O / △ / X**, 종합은 4단계.

| 평가 항목 | 확인 내용 |
|---|---|
| 레이아웃 타당성 | 조회영역/결과영역/버튼영역 등이 화면 유형 패턴(`catalog/layout-guide.md`)에 맞게 배치됐나 |
| 컴포넌트 적합성 | 표→`w2:gridView`, 입력칸→`w2:inputBox`, 날짜→`w2:calendar` 등 의도대로 매핑됐나 (§7) |
| 사내 표준 준수 | `componentKey`/`tokenKey` 사용, 필수(＊) 규칙, 버튼 우측 정렬·역할별 색상 |
| 텍스트 정확도 | 라벨/표 컬럼명이 캔버스에 입력한 대로 나왔나 |
| 미확정 처리 | 애매한 부분을 추측으로 채우지 않고 `questions` 로 물었나 |
| WebSquare XML | well-formed, Preview 렌더 가능, `report.fallbacksApplied` 내용 타당 |

**종합 등급**: `4 그대로 사용` / `3 소폭 수정 후 사용` / `2 대폭 수정 필요` / `1 사용 불가`

| 케이스 | 레이아웃 | 컴포넌트 | 표준 준수 | 텍스트 | 미확정 | XML | 종합 | 코멘트 |
|---|:--:|:--:|:--:|:--:|:--:|:--:|:--:|---|
| N-LIST | | | | | | | | |
| N-DETAIL | | | | | | | | |
| N-FORM | | | | | | | | |
| N-POPUP | | | | | | | | |
| N-MAIN | | | | | | | | |
| N-BLANK | | | | | | | | |
| E-QUERY | | | | | | | | |
| E-MAIN | | | | | | | | |

> **판정(안)**: 신규 6종 중 4종 이상 + 변경 1건 이상이 종합 3 이상이면 SC-1 충족.

## 5. 시간 단축 (SC-3)

동일 화면 3건에 대해 측정. 수작업 = 기존 방식(WebSquare 편집기 직접 작성) 기준 추정/실측.

| 화면 | 수작업(분) | 하이스케치(분) | 비고 |
|---|---|---|---|
| 목록 조회 화면 | | | 스케치 + 생성 + 소폭 수정까지 |
| 등록 · 수정 화면 | | | |
| 팝업 화면 | | | |

- 하이스케치 소요 = (캔버스 스케치) + (생성 대기, 재시도 포함) + (결과 소폭 수정)
- 생성 자체 소요는 `report.elapsedMs` 참고

> **판정(안)**: 3건 평균에서 하이스케치가 유의미하게 짧으면 SC-3 충족.

## 부록. 케이스 실행 절차

1. `npm run dev` → http://localhost:3000
2. 시스템 선택 → 작업 구분(신규/변경) → 유형/화면 선택
3. 표 "캔버스 구성" 대로 편집, "보충 설명"에 note 입력
4. **화면 생성** → 결과 모달에서 [화면]·[전달 데이터]·[WebSquare XML] 확인, 내려받기
5. `runs/<timestamp>/` 폴더명을 §1 표에 기록
6. §3 정성 평가 표 작성
7. CONSIST: 3·4번을 입력 변경 없이 3회 반복
