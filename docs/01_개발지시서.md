## 0. 이 문서에 대하여

- **독자**: 이 프로젝트를 구현하는 담당자 2인(및 Claude Code 세션).
- **목적**: 이 문서 하나로 PoC 개발에 착수하고 2인이 병행 작업할 수 있도록, 제품 개념·데이터 계약·역할 분담·작업 목록·수락 기준을 지시 형태로 정의한다.
- **사용법**: 개발 요청 시 "§N을 구현하라", "T-x 작업" 처럼 이 문서의 번호를 참조한다. 문서와 코드가 어긋나면 이 문서를 우선하되, 발견 즉시 문서를 갱신한다.
- **예시 UI**: `samples/화면스케치스튜디오_예시_v1.html` 은 **완성해야 할 UX·데이터 흐름의 기준 프로토타입**이다. 편집기 동작, 좌측 패널 구성, `payload()` 형태, 결과 모달(화면/전달 데이터/WebSquare XML 탭)은 이 파일의 동작을 계승한다. 단, 예시의 `compile()` 은 AI 없이 만든 임시 변환기이며 실제로는 §4의 파이프라인으로 대체한다.
- **미결정 항목**: §12에 기본값을 함께 명시했다. 별도 지시가 없으면 기본값으로 진행하고 결과를 §12 표에 기록한다.

## 1. 프로젝트 목표 · 제품 개념

기획자·현업이 **캔버스에 화면을 대충 그리면**, AI가 **사내 UI 표준으로 정리한 화면 초안과 코드(WebSquare XML)** 를 만들어 주는 웹 도구를 1개월 안에 동작하는 형태로 구현한다.

핵심 가치:
1. **직접 편집 가능한 캔버스** — 요소를 클릭해서 놓고, 드래그·리사이즈·정렬하고, 문구/필수 여부/항목을 바로 고친다. (반듯하지 않아도 됨)
2. **화면 생성 요청** — "화면 생성" 클릭 시 캔버스 내용 + 보충 설명 + 첨부 파일을 AI로 보내 사내 표준 화면으로 정리.
3. **결과 출력** — 정리된 화면 Preview + WebSquare XML 코드 + 전달 데이터(JSON)를 확인·복사·다운로드.

작업 구분: **신규화면**(화면 유형 템플릿에서 시작) / **변경화면**(기존 화면을 불러와 수정). 대상 화면 유형: **목록 조회 / 상세 조회 / 등록·수정 / 팝업 / 메인 / 빈 화면**. 대상 시스템: 하이포탈 / 영업포탈 / 하이콜 (PoC 범위) — **계속 추가되므로 검색형 콤보박스로 선택**한다.

PoC 성공 판정: 위 3가지가 대상 화면 유형별로 재현되고 §11 수락 기준을 만족하면 1차 목표 달성으로 본다.

## 2. 사용자 흐름 (예시 UI 기준)

```
① 시스템 선택 — 검색 가능한 콤보박스(드롭다운 + 타입어헤드). 시스템은 계속 추가될 수 있음
② 작업 구분 선택 — 신규화면 / 변경화면
   - 신규화면: ③-a 화면 유형 선택 표시
   - 변경화면: ③-b 변경할 화면 선택(콤보박스, 선택한 시스템으로 필터) 표시
③-a (신규) 화면 유형 선택 (목록조회 / 상세조회 / 등록수정 / 팝업 / 메인 / 빈 화면)  → 템플릿 프리셋이 캔버스에 로드(빈 화면은 아무것도 없이 시작)
③-b (변경) 변경할 화면 선택 → 해당 화면의 기존 배치를 캔버스에 로드(수정 대상). **변경 모드에는 화면 유형 선택이 없다**(완성된 화면을 고치는 것이므로 불필요)
④ 캔버스 편집
   - 좌측 팔레트에서 요소 클릭 → 캔버스에 배치
     (제목 / 글자 / 입력칸 / 선택 / 라디오 / 날짜 / 체크 / 긴 글 / 파일 / 표 / 페이지 / 탭 / 이미지 / 버튼 / 구분선 / 묶음)
   - 드래그 이동, 8방향 리사이즈, 정렬 스냅 가이드, 겹침 순서
   - 다중 선택: Shift+클릭 / 빈 곳 드래그(마퀴). 선택 묶음 이동·복제·삭제
   - 요소 1개 선택 시 플로팅 툴바: 문구 편집, 항목(표/선택) 편집, 필수(＊) 토글, 복제, 맨 앞/뒤, 삭제
   - 요소 2개 이상 선택 시 플로팅 툴바: 정렬(좌·중·우 / 상·중·하), 균등 분배(가로/세로, 3개 이상)
   - 단축키: Ctrl+Z/Y(되돌리기·다시), Ctrl+C/V, Ctrl+D(복제), Ctrl+A(전체 선택), Del, Esc, 방향키(1px / Shift 10px)
   - 하단 툴바: 되돌리기/다시, 확대·축소(50~150%), 전체 비우기, 단축키 도움말(?)
   - 첫 방문 시 온보딩 코치 카드(1회, 닫으면 다시 안 뜸)
⑤ 보충 설명 입력 (화면으로 그리기 어려운 규칙) + 참고 파일 첨부 (Excel · PPT · 이미지)
⑥ "화면 생성" 클릭
   → 캔버스 payload 를 백엔드로 전송 → Stage A(정규화) → Stage B(코드 생성) → 자동 검증 루프
⑦ 결과 모달
   - [화면] 탭: 생성된 화면 Preview (iframe)
   - [전달 데이터] 탭: AI로 보낸 payload(JSON)
   - [WebSquare XML] 탭: 생성된 XML 코드
   - 내려받기 (zip)
⑧ (선택) Stage A 질문에 답하거나 자연어로 수정 요청 → 재생성
```

> **변경화면 모드**: Stage A/B 는 payload 의 `mode=edit` 와 `baseScreen` 을 인지해 "기존 화면 대비 변경분"으로 처리한다. 변경할 화면의 기존 정의(shapes/코드)는 §12 OI-11 의 데이터 소스에서 가져온다.

"임시저장"(작업 중 캔버스 보관)과 "샘플"(예시 화면 로드)도 예시대로 제공한다.

## 4. 아키텍처

### 4.1 구성

- **프론트엔드(에디터)**: 예시를 계승한 단일 페이지 앱. 기본은 **바닐라 JS**(빌드 없이 동작), 모듈 분리는 허용. React 전환은 범위 밖(§12 OI-2).
- **백엔드**: Node.js(LTS) + Express. LLM 호출, 파이프라인 오케스트레이션, 첨부 파싱, XML 검증, 로그 저장.
- **LLM 호출은 전부 백엔드에서만.** 키를 프론트엔드로 노출하지 않는다.

### 4.2 파이프라인 (2-Stage)

| 단계 | 입력 | 처리 | 출력 |
|---|---|---|---|
| **Stage A — 정규화/해석** | 화면정의 payload + 보충 설명 + 첨부(파싱 결과) + 사내 표준 카탈로그 | 러프한 좌표를 정렬된 행/섹션/그리드로 정리, 요소를 사내 표준 `componentKey`/`tokenKey` 로 매핑, 조회영역·결과영역 등 유형별 패턴 적용, 불명확·누락 요소를 `confidence`/`questions` 로 표기 | 정규화 IR(JSON) |
| **Stage B — 코드 생성** | 정규화 IR + 카탈로그 + 대상 시스템 | WebSquare XML 생성(표준 컴포넌트 우선, 토큰 스타일), 화면 Preview용 HTML 생성, 더미 데이터/핸들러 stub, 실제 API 연동 없음 | `screen.xml`, `preview.html`, `report.json` |
| **자동 검증 루프** | Stage B 산출물 | XML well-formedness + (가능 시)WebSquare 스키마 검증 + HTML 렌더 sanity. 실패 시 검사 결과를 모델에 재입력해 수정, **최대 3회**(설정) | 정상화된 산출물 또는 오류 로그 |

- **IR 을 고정 스키마로 둔다** — 모델 교체·품질 비교·회귀 테스트를 쉽게 하기 위함.
- **결정론적 폴백 변환기(D-7)** 는 Stage B 를 AI 없이 대체할 수 있어야 한다: AI 장애/오프라인 시 동작, 그리고 AI 산출물 회귀 판단의 기준선.

## 5. 역할 분담 (2인)

두 사람의 경계는 **§6 데이터 계약**이다. 계약을 먼저 확정하고, 각자 상대편을 mock 으로 두고 병행 개발한다.

### 5.1 담당 1 — AI 통신 / 생성 백엔드

**책임 범위**
- Express 서버, `POST /api/generate` (payload 수신 → 결과 반환), `POST /api/refine`(질문 답변/수정 요청 반영 재생성).
- **메타 API**: `GET /api/systems`(시스템 목록), `GET /api/screens?system=&q=`(변경화면 목록, 검색어 필터), `GET /api/screens/:id`(기존 화면 정의 → shapes 로 변환). PoC 는 `fixtures/` 기반 mock 데이터로 시작(§12 OI-11).
- LLM Provider 추상화(§9), 기본 provider = Claude. OpenAI 어댑터 stub.
- **Stage A**: payload → 정규화 IR. 좌표 정렬/그룹핑 보정, 사내 표준 매핑, 유형별 패턴 적용, 미확정 표기 + `questions[]` 생성. `mode=edit` 시 `baseScreen` 대비 변경분으로 해석.
- **Stage B**: IR → WebSquare XML + Preview HTML + `report.json`.
- **자동 검증 루프**: XML/HTML 정적 검사 → 실패 시 재수정(최대 3회).
- **첨부 파일 파싱**: 이미지(멀티모달로 화면 파악), Excel 화면정의서/PPT(텍스트·표 추출)를 Stage A 컨텍스트로 주입.
- **결정론적 폴백 변환기(D-7)**: payload→XML/HTML 기준 변환(예시 `compile()` 발전형).
- 사내 표준 카탈로그의 **WebSquare 매핑 규칙(§7)** 정의·관리.
- 세션 로그(D-8), 토큰/비용 로깅.

**완료의 정의**: mock payload(fixtures) 입력만으로 §6 결과 스키마에 맞는 XML/Preview/report 를 반환하고, 자동 검증 루프가 동작한다.

### 5.2 담당 2 — UI 환경 / 캔버스 에디터

**책임 범위** (예시 UI 계승)
- **상단 바**: 로고, 화면명 입력, 샘플/임시저장/화면 생성 버튼.
- **좌측 패널**:
  - **시스템 선택**: 검색형 콤보박스(재사용 컴포넌트 `combobox`). 항목 다수 대비 타입어헤드 필터.
  - **작업 구분**: 세그먼트 `신규화면 / 변경화면`.
  - **신규화면 선택 시**: 화면 유형 템플릿 4종 표시(목록조회/상세조회/등록수정/팝업).
  - **변경화면 선택 시**: "변경할 화면" 콤보박스 표시(같은 `combobox` 컴포넌트, 선택된 시스템으로 필터). 선택 시 해당 화면의 기존 배치를 캔버스에 로드.
  - 요소 팔레트 10종, 보충 설명 textarea, 참고 파일 드롭존 + 목록.
- **캔버스**: 고정 보드(기본 960×600, 유형별 크기는 §12 OI-6), 그리드 배경, 요소 배치.
- **요소 조작**: 선택, 드래그 이동(보드 경계 clamp), 8방향 리사이즈, 정렬 스냅 가이드(중심/모서리, 임계 6px)와 가이드 라인 표시, z-order.
- **다중 선택**: Shift+클릭 토글, 빈 곳 마퀴 드래그(교차 선택, Shift 로 누적). 묶음 이동(경계 clamp)·복제·삭제·z-order.
- **플로팅 컨텍스트 툴바**: (1개) 문구 편집, 항목 편집(표/선택), 필수(＊) 토글, 복제, 맨 앞/맨 뒤, 삭제 / (2개+) 정렬(좌·중·우 / 상·중·하), 균등 분배(가로/세로, 3개 이상).
- **하단 툴바**: 되돌리기/다시(히스토리 60단계), 확대·축소(50~150%), 전체 비우기, 단축키 도움말(?).
- **온보딩**: 첫 방문 시 코치 카드 1회 노출(`localStorage: hds:coachDone`).
- **단축키**: Ctrl+Z/Y, Ctrl+C/V, Ctrl+D, Ctrl+A(전체 선택), Del/Backspace, Esc, 방향키(1px / Shift 10px).
- **템플릿 프리셋**: 목록조회/상세조회/등록수정/팝업 초기 배치(신규화면 모드).
- **변경화면 로드**: 선택한 기존 화면의 정의를 shapes 로 변환해 캔버스에 로드(변경화면 모드).
- **화면 생성 호출**: payload 를 만들어 `/api/generate` 호출, 진행 단계 표시, 결과 모달 렌더.
- **결과 모달**: [화면] iframe Preview, [전달 데이터] payload JSON, [WebSquare XML] 코드(구문 강조), 내려받기(zip), 클립보드 복사.
  - [화면] 탭 보기 전환: **결과 / 내 스케치 / 나란히** — 생성 요청 시점의 캔버스 스냅샷과 생성 결과를 비교(변경 전후 확인).
- **질문/수정 UI**: Stage A 질문 표시 → 답변 → `/api/refine` 호출, 자연어 수정 입력.
- **임시저장**: localStorage(최소) 기반 캔버스 저장/복원. **샘플**: 예시 샘플 화면 로드.

**완료의 정의**: mock result(fixtures)만으로 편집→payload 생성→결과 모달 표시까지 전 구간이 동작한다.

### 5.3 인터페이스 계약

| 방향 | 아티팩트 | 소유 |
|---|---|---|
| 담당 2 → 담당 1 | **화면정의 payload** (`schemas/screen-draft.schema.json`) — `/api/generate` 요청 본문 | 공동 관리, 변경 시 양자 합의 |
| 담당 1 → 담당 2 | **생성결과** (`schemas/generation-result.schema.json`) — `/api/generate` 응답 | 공동 관리 |
| 담당 2 → 담당 1 | **수정 요청** (`schemas/refine-request.schema.json`) — `/api/refine` 요청(원본 payload + 질문 답변/자연어) | 공동 관리 |

계약 상세는 §6. 스키마 변경은 PR + 양자 리뷰 필수. `fixtures/` 의 mock 파일도 함께 갱신한다.

### 5.4 병행 개발 전략

1. **1주차 공동 작업**: §6 스키마 3종 + `fixtures/` mock 샘플(유형별 payload/result 각 1개 이상, 시스템 목록, 변경화면 목록·정의) + `catalog/` 최소 골격 + 프로젝트 스캐폴딩 확정.
2. 이후 각자 진행:
   - 담당 2 는 `/api/generate`·메타 API 를 `fixtures/` 를 그대로 돌려주는 mock 서버로 대체해 UI 완성.
   - 담당 1 은 `fixtures/` payload 를 입력으로 파이프라인 완성.
3. **3주차 통합**: mock 제거, 실제 연동. 계약 불일치는 스키마/픽스처를 정본으로 조정.
4. 공용 영역(`schemas/`, `catalog/`, `fixtures/`, `src/shared/`)은 작은 PR + 상호 리뷰.

## 7. 컴포넌트 ↔ 사내 표준(WebSquare) 매핑

Stage B / 폴백 변환기의 기준. 상세·시스템별 차이는 `catalog/websquare/` 에 관리.

| 팔레트 요소 | 의미 | WebSquare (기준) | 비고 |
|---|---|---|---|
| 입력칸 `input` | 텍스트 입력 | `<w2:inputBox>` | 필수 시 `class="w2input_essential"` |
| 선택 `select` | 드롭다운 | `<w2:selectBox dataList="...">` | `items` → 옵션 목록 |
| 라디오 `radio` | 라디오 그룹 | `<w2:radiobutton dataList="...">` | `items` → 옵션 목록 |
| 날짜 `date` | 날짜 선택 | `<w2:calendar displayFormat="yyyy-MM-dd">` | |
| 체크 `check` | 체크박스 | `<w2:checkbox label="...">` | |
| 긴 글 `text` | 여러 줄 입력 | `<w2:textarea>` | |
| 파일 `file` | 파일 업로드 필드 | `<w2:fileUpload>` | 화면 안의 첨부 컴포넌트(도구의 참고 파일과 무관) |
| 표 `list` | 그리드 | `<w2:gridView>` + `<w2:gridColumn>` × n | `items` → 컬럼 |
| 페이지 `pager` | 페이지네이션 | `<w2:pagination>` | 보통 그리드 하단 |
| 탭 `tab` | 탭 컨트롤 | `<w2:tabControl>` + `<w2:tabItem>` × n | `items` → 탭 이름 |
| 이미지 `image` | 이미지/아이콘 자리 | `<w2:image alt="...">` | |
| 버튼 `button` | 실행 | `<w2:trigger value="..." onclick="fn_...">` | 문구로 조회/저장 등 역할 추론 |
| 구분선 `divider` | 가로 구분선 | `<w2:group class="w2group_divider">` | 스타일상의 선 |
| 글자 `label` | 항목명 | `<w2:textbox>` (읽기) | 필수 표시 규칙 적용 |
| 제목 `title` | 섹션 제목 | 섹션 헤더 + `<w2:textbox>` | |
| 묶음 `area` | 레이아웃 그룹 | `<w2:group>` / 레이아웃 컨테이너 | 내부 요소를 행으로 그룹핑 |

- 표준에 없는 형태는 `config/policy.json` 의 fallback 규칙으로 대체하고 `report.fallbacksApplied` 에 기록.
- 금지 컴포넌트는 결과에서 배제.
- 색/간격/타이포는 `catalog/tokens.json` 의 `tokenKey` 로 치환.

## 9. LLM 연동 규격

### 9.1 Provider 인터페이스

```
generateStructured({ system, messages, images?, jsonSchema }) -> { json, usage }
generateText({ system, messages }) -> { text, usage }
```

- Stage A = `generateStructured` (필요 시 이미지 포함, `jsonSchema` = IR 스키마).
- Stage B = `generateText` 또는 구조화 출력(파일 묶음).
- 공통: `provider`, `model`, timeout, 재시도(지수 백오프), `usage`(토큰/비용) 로깅.

### 9.2 설정 (env)

| 변수 | 용도 |
|---|---|
| `LLM_PROVIDER_STAGE_A` / `LLM_PROVIDER_STAGE_B` | `claude`(기본) 또는 `openai` |
| `LLM_MODEL_STAGE_A` / `LLM_MODEL_STAGE_B` | 모델 ID |
| `ANTHROPIC_API_KEY` / `OPENAI_API_KEY` | 키. **소스 하드코딩 금지**, `.env` 만 |
| `AUTOFIX_MAX_RETRIES` | 자동 검증 루프 횟수(기본 3) |

기본값으로 두 단계 모두 Claude 사용. 최종 모델 선정을 위해 PoC 초기에 동일 입력셋 provider A/B 비교 1회(§8 A-11).

## 10. 제약사항 · 보안

### 10.1 기술
- 상용 LLM API 사용(자체 모델 학습·호스팅 없음).
- Stage A 출력(IR)은 JSON Schema 로 고정.
- **생성 코드 타겟은 WebSquare XML 로 고정.** Preview HTML 은 화면 확인용. 그 외 타겟은 범위 밖.
- Preview HTML 은 최신 Chrome/Edge 에서 추가 빌드 없이 렌더.
- 에디터는 빌드 없이 동작(바닐라 JS 기본).

### 10.2 데이터 · 보안
- **사내 영업포탈의 샘플 코드/이미지를 반입하지 않는다.** 외부 공개 샘플 기준으로 아키텍처를 잡는다.
- PMS 소스 활용 안은 취소됨. 대체 방안 재검토 중(§12 OI-5).
- 사내 UI 표준 카탈로그는 PoC 용 최소 범위만 별도 정리해 사용.
- 입력 캔버스·설명·첨부에 사내 기밀/개인정보가 포함되지 않도록 에디터에 가이드 문구 표시.
- API 키는 소스 하드코딩 금지, `.env` 만. 입력·산출물은 로컬/PoC 환경 내에서만 취급.
- 상용 API 전송 데이터의 범위·보관 정책 사전 확인(§12 OI-7).

### 10.3 가정
- 대상 화면 유형별 참조 자료·기대 결과가 확보된다.
- 사내 UI 표준(WebSquare 매핑 포함) 최소 세트를 PoC 기간 내 정의 가능하다.
- WebSquare 스키마/샘플을 외부 공개 수준에서 확보 가능하다.
- LLM API 사용 한도/비용이 PoC 수행에 충분하다.

## 11. 수락 기준 (Acceptance Criteria)

기능적 기준은 아래 AC 표. **성공 판정 기준(SC-1 사용 가능한 초안 / SC-2 스타일 일관성 / SC-3 시간 단축)과 평가 케이스·체크리스트는 [`docs/03_평가결과.md`](03_평가결과.md) 에 정의**되어 있으며, T-6 에서 실행·기록한다.

| # | 기준 |
|---|---|
| AC-1 | `npm install && npm run dev` 만으로 에디터 + 백엔드가 로컬 구동된다. |
| AC-2 | 예시 UI 의 편집 기능(배치·이동·리사이즈·스냅·컨텍스트 툴바·undo/redo·zoom·단축키·템플릿)이 모두 동작한다. |
| AC-2b | 시스템·변경화면이 검색형 콤보박스로 선택되고, 신규 모드에서만 화면 유형이 노출된다. 유형 5종(목록/상세/등록수정/팝업/메인) 클릭 시 각기 다른 프리셋이 캔버스에 로드된다. |
| AC-2c | 변경화면에서 기존 화면(시스템별 메인/조회)을 선택하면 그 화면의 배치가 캔버스에 로드되고, 다른 화면으로 바로 전환된다(수정 전이면 확인 없이). |
| AC-3 | "화면 생성" 시 §6.1 스키마를 통과하는 payload(`mode`·`systemId`·신규 `template` / 변경 `baseScreen` 포함)가 백엔드로 전송된다. |
| AC-4 | `docs/03_평가결과.md` 의 신규 케이스(N-*) + 변경 케이스(E-*) 각각에 대해 Stage A 가 스키마를 통과하는 IR 을 생성한다. |
| AC-5 | 각 케이스에서 결과 모달의 [화면]·[전달 데이터]·[WebSquare XML] 탭이 렌더되고, 내려받은 파일이 단독으로 열린다. |
| AC-6 | 생성 XML 이 well-formed 이고, 사내 표준 `componentKey`/`tokenKey` 를 사용하며 미사용 시 `report` 에 사유가 남는다. |
| AC-7 | 자동 검증 루프가 최대 3회로 제한되고, 실패 시 오류 로그가 사용자에게 노출된다. |
| AC-8 | Stage A 질문에 답하거나 자연어 수정을 하면 반영된 결과로 재생성된다. |
| AC-9 | AI 장애 시 결정론적 폴백 변환기로 XML/Preview 가 생성되고 `report.usedDeterministicFallback=true` 로 표시된다. |
| AC-10 | 동일 입력 3회 반복 시 표준 컴포넌트/토큰 사용 구조가 정성 평가에서 크게 흔들리지 않는다. |
| AC-11 | 생성 1건마다 `runs/<timestamp>/` 에 payload·ir·output·report 가 저장된다. |
| AC-12 | API 키가 프론트엔드 번들·응답·로그에 노출되지 않는다. |
| AC-13 | 단일 화면 생성(생성 클릭 → Preview)이 통상 3분 이내(재시도 포함). |
| AC-14 | `docs/03_평가결과.md` 의 모든 케이스 실행 결과와 위 기준 충족 여부, SC-1~3 판정이 정리된다. |
