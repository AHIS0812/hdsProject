## 1. 프로젝트 목표

1개월 안에 아래 3가지를 동작하는 형태로 구현하고, 정식 개발 전환 여부를 판단할 근거를 만든다.

1. **자연어(및 가능 시 이미지) 입력 → 사내 UI 표준 기반 단일 화면 초안 생성**
2. **생성 화면 Preview 제공** (브라우저 렌더링)
3. **생성 소스(HTML 등) 확인 · 복사 · 다운로드**

이 세 가지가 대상 화면 3종(팝업 / 모니터링 전체조회 / 메인화면)에 대해 재현되면 PoC 1차 목표 달성으로 본다.

## 3. 처리 흐름

```
[입력]                        [Stage A: 구조 분석]          [사내 UI 표준]
 - 자연어 프롬프트     ──▶     멀티모달 LLM        ──▶  IR(JSON)  +  카탈로그/토큰
 - (선택) 스케치/스크린샷       · 레이아웃 계층 추론                    │
 - (선택) 화면 유형 프리셋      · 컴포넌트 타입/배치 추론                ▼
                              · 텍스트(라벨/컬럼) 인식        [매핑] IR 컴포넌트 → componentKey/tokenKey
                              · 확신도/미확정 표기 + 질문 생성          │
                                                                      ▼
                                                          [Stage B: 코드 생성] 코드 생성 LLM
                                                           · 표준 컴포넌트 우선 매핑
                                                           · 레이아웃/토큰 스타일 구현
                                                           · 더미 데이터/핸들러 stub
                                                           · 정적 검사 실패 시 자동 수정 (최대 3회)
                                                                      │
                                                                      ▼
                                                    [산출물] Preview · 소스(HTML 등) · ir.json · report.json
```

단계 분리 이유: Stage A는 "이미지·자연어 이해와 불확실성 처리", Stage B는 "표준 준수 + 오류 없는 코드 생성"으로 역량이 다르며, IR을 고정 스키마로 두면 모델 교체·품질 비교가 쉬워진다.

## 4. 아키텍처 및 기술 스택

### 4.1 런타임 구성

- **백엔드**: Node.js (LTS) + Express. LLM API 호출, 파이프라인 오케스트레이션, 정적 검사, 로그 저장 담당.
- **프론트엔드**: 단일 페이지 웹 UI. 백엔드가 정적 파일로 서빙.
- LLM 키가 프론트엔드로 노출되지 않도록 **모든 LLM 호출은 백엔드에서만** 수행한다.

### 4.2 생성물 타겟 스택 (설정값)

`config/targets.json` 로 지정하며 두 가지를 지원한다.

| 타겟 | 기본값 | 산출물 |
|---|---|---|
| `static-html` | **✅ 기본** | `screen.html` + 필요 시 `styles.css`, `tokens.css`. 빌드 없이 Chrome/Edge 렌더링. |
| `react-vite-ts` | 옵션 | `App.tsx` 등 컴포넌트 파일 + `package.json`. Preview는 백엔드가 임시 Vite 빌드 or esbuild 트랜스파일 후 렌더. |

PoC 평가는 `static-html` 기준으로 우선 수행한다. `react-vite-ts` 는 파이프라인이 타겟에 따라 프롬프트/후처리만 바꾸면 되도록 구조화하고, 최소 1개 화면으로 동작 확인만 한다.

### 4.3 프로젝트 구조 (권장)

```
hdsProject/
├─ src/
│  ├─ server/            # Express, 라우트(/api/generate 등)
│  ├─ pipeline/          # stageA.js, mapping.js, stageB.js, autofix.js
│  ├─ llm/               # provider 추상화 (§8)
│  └─ web/               # 프론트엔드 (입력/Preview/소스뷰/다운로드)
├─ schemas/ir.schema.json
├─ catalog/              # components.json, tokens.json, layout-guide.md, snippets/
├─ prompts/stage-a.md, stage-b.md
├─ config/targets.json, policy.json
├─ runs/                 # 세션 로그 (gitignore)
├─ samples/screens/      # 대상 화면 3종 참조 이미지 (외부 공개 샘플만)
└─ docs/
```

## 5. 구현 작업 목록 (Task Breakdown)

우선순위: **M**(필수) / **S**(가능 시) / **C**(여유 시). 각 작업은 "완료 조건"을 만족해야 종료.

### T-1. 프로젝트 스캐폴딩 · 서버 (M)
- Express 서버, 프론트엔드 정적 서빙, `.env` 로딩(dotenv), `npm run dev`.
- **완료 조건**: 로컬에서 빈 입력 폼 페이지가 뜬다.

### T-2. LLM Provider 추상화 (M)
- §8의 인터페이스 구현. 기본 provider = Claude. OpenAI provider 는 어댑터 stub 까지.
- 타임아웃·재시도·토큰/비용 로깅 포함. 키는 env 에서만 읽는다.
- **완료 조건**: 텍스트 프롬프트 1건이 provider 통해 왕복하고 토큰 수가 로그에 남는다.

### T-3. IR 스키마 확정 (M)
- `schemas/ir.schema.json` 작성 (§7 기반, JSON Schema draft 2020-12).
- 검증 유틸(`validateIR`) — 실패 시 오류 경로를 사람이 읽을 수 있게 반환.
- **완료 조건**: §7 예시 JSON 이 스키마를 통과하고, 필드 누락 케이스는 명확한 오류를 낸다.

### T-4. PoC용 사내 UI 표준 카탈로그 (M)
- `catalog/components.json`: `componentKey`, 표시명, 파라미터/슬롯, HTML snippet(경로).
- `catalog/tokens.json`: `tokenKey`, 값(색/간격/타이포/라운드).
- `catalog/layout-guide.md`: 그리드 규칙, 간격 스케일, 화면 유형별 템플릿.
- 범위: 대상 화면 3종에 실제로 필요한 컴포넌트/토큰만. 외부 공개 가능한 수준으로 직접 정의(사내 실자산 반입 금지, §10).
- **완료 조건**: 3종 화면 초안에 쓰일 컴포넌트가 카탈로그에 모두 존재하거나 fallback 규칙이 명시돼 있다.

### T-5. Stage A — 구조 분석 → IR (M)
- 입력: 자연어(필수) + 이미지(선택, PNG/JPG) + 화면 유형 프리셋(선택).
- 출력: §7 IR. 응답 포맷 강제(JSON schema/response format 옵션)를 사용한다.
- 불명확·누락 요소: `confidence` 표기 + `questions[]` 로 분리.
- 이미지 품질 문제 감지 시 재촬영/전처리 가이드 메시지 반환 (S).
- **완료 조건**: "조회 조건 3개와 결과 테이블이 있는 모니터링 화면" 같은 자연어로 스키마를 통과하는 IR 이 나온다.

### T-6. 표준 매핑 (M)
- IR 각 컴포넌트 → `componentKey` 매핑, 스타일 값 → `tokenKey` 치환.
- 표준에 없으면 `policy.json` 의 fallback 규칙 적용 후 `report.json` 에 대체 사실 기록.
- `policy.json` 의 금지 컴포넌트는 결과에서 배제 (S).
- **완료 조건**: 매핑 후 IR 의 모든 컴포넌트가 `componentKey` 를 갖거나 fallback 표기가 있다.

### T-7. Stage B — 코드 생성 (M)
- 입력: 매핑된 IR + 카탈로그 + 타겟 스택 + 정책.
- 출력: 타겟별 소스. 표준 컴포넌트 우선, 토큰 기반 스타일, 더미 데이터/핸들러 stub, 실제 API 연동 없음.
- 기본 접근성 속성(aria/label), 기본 반응형, lint/format 규약 준수 (S).
- **완료 조건**: `static-html` 타겟에서 `screen.html` 이 브라우저에 렌더된다.

### T-8. 자동 수정 루프 (M)
- Stage B 산출물에 정적 검사(HTML 파싱/유효성, TS 타입체크, 기본 레이아웃 sanity) 수행.
- 실패 시 검사 결과를 모델에 재입력해 수정. **최대 3회**(`config` 로 조정). 실패 시 마지막 결과 + 오류 로그 제시.
- **완료 조건**: 의도적으로 깨진 산출물이 루프를 거쳐 정상화되거나, 3회 후 오류 로그와 함께 종료된다.

### T-9. Preview (M)
- 생성 화면을 UI 안에서 렌더링. 데스크톱 뷰 기본, 모바일/태블릿 뷰는 토글 (C).
- 렌더 실패 시 오류 메시지 + 원인 소스 위치 표시 (S).
- **완료 조건**: 생성 직후 Preview 가 자동 표시된다.

### T-10. 소스 확인 · 활용 (M)
- 생성 소스 구문 강조 뷰, 클립보드 복사, 파일 다운로드(zip).
- `ir.json`, 미확정 항목 리스트도 함께 확인·다운로드 (S).
- **완료 조건**: 복사·다운로드가 동작하고 다운로드한 `screen.html` 이 단독으로 열린다.

### T-11. 확인·수정 루프 (UI) (M)
- Stage A 질문에 사용자가 답하면 IR 갱신 후 재생성.
- 자연어 수정 요청 반영 재생성 (S).
- **완료 조건**: 질문 1건에 답하면 반영된 IR 로 재생성된다.

### T-12. 세션 로그 · 평가 export (S)
- `runs/<timestamp>/` 에 input, ir.json, output, report.json 저장.
- 케이스별 소요시간·표준 사용 일관성 지표를 CSV/JSON 으로 export.
- **완료 조건**: 생성 1건이 끝나면 `runs/` 에 폴더가 생기고 필수 파일이 들어 있다.

### T-13. 대상 화면 3종 실행 · 평가 (M)
- 팝업 / 모니터링 전체조회 / 메인화면 각각 참조 이미지·자연어로 생성.
- §11 수락 기준 충족 여부를 `docs/03_평가결과.md` 에 정리.
- **완료 조건**: 3종 모두 Preview + 소스 산출, 평가 문서 작성 완료.

## 7. IR 데이터 포맷

Stage A 출력. `schemas/ir.schema.json` 이 정본이며 아래는 형태 예시.

```jsonc
{
  "screen": { "type": "popup | monitoring-list | main | custom", "title": "..." },
  "layout": [
    {
      "id": "sec-1",
      "kind": "section | grid | container",
      "children": ["cmp-1", "cmp-2"],
      "props": { "columns": 12, "gap": "md" }
    }
  ],
  "components": [
    {
      "id": "cmp-1",
      "type": "button | input | table | card | select | text | ...",
      "parentId": "sec-1",
      "position": { "order": 1, "align": "left" },
      "text": { "label": "조회", "placeholder": null },
      "componentKey": null,     // Stage A 는 후보/null, 매핑 단계에서 확정
      "tokenKeys": [],
      "confidence": 0.82,
      "uncertain": false
    }
  ],
  "questions": [
    { "targetId": "cmp-3", "question": "이 영역은 그리드입니까, 카드 리스트입니까?", "options": ["grid", "card-list"] }
  ]
}
```

산출물 파일:
- `screen.html` (+ `styles.css` / `tokens.css` 필요 시) 또는 타겟별 컴포넌트 파일
- `ir.json`
- `report.json` — 재시도 횟수, 처리 시간, 미확정 항목, fallback 적용 목록

## 8. LLM 연동 규격

### 8.1 Provider 인터페이스

```
generateStructured({ system, messages, images?, jsonSchema }) -> { json, usage }
generateText({ system, messages }) -> { text, usage }
```

- Stage A = `generateStructured` (멀티모달, `jsonSchema` = IR 스키마).
- Stage B = `generateText` (또는 파일 묶음 반환용 구조화 출력).
- 공통: `provider`, `model`, timeout, 재시도(지수 백오프), `usage`(토큰/비용) 로깅.

### 8.2 설정 (env)

| 변수 | 용도 |
|---|---|
| `LLM_PROVIDER_STAGE_A` / `LLM_PROVIDER_STAGE_B` | `claude`(기본) 또는 `openai` |
| `LLM_MODEL_STAGE_A` / `LLM_MODEL_STAGE_B` | 모델 ID |
| `ANTHROPIC_API_KEY` / `OPENAI_API_KEY` | 키. **소스 하드코딩 금지**, `.env` 만. |

기본값으로 두 단계 모두 Claude 를 사용한다. Stage A/B 모델 최종 선정을 위해 PoC 초기에 동일 입력셋으로 provider A/B 비교를 1회 수행하고 결과를 §12 에 기록한다.

## 9. 사내 UI 표준 카탈로그 형식

- **컴포넌트 카탈로그** (`catalog/components.json`): `componentKey`, 표시명, 파라미터/슬롯, 사용 예시 HTML snippet(`catalog/snippets/<key>.html`).
- **디자인 토큰** (`catalog/tokens.json`): `tokenKey`, 값(색상/간격/타이포/라운드 등).
- **레이아웃 가이드** (`catalog/layout-guide.md`): 그리드 규칙, 간격 스케일, 화면 유형별 템플릿.
- **정책** (`config/policy.json`): 허용/금지 컴포넌트, fallback 규칙.

## 10. 제약사항 및 가정

### 10.1 기술
- 상용 LLM API 사용 (자체 모델 학습·호스팅 없음).
- Stage A 출력(IR)은 JSON Schema 로 고정.
- 생성물 기본 타겟은 정적 HTML + CSS, 프레임워크는 옵션.
- 생성 HTML 은 최신 Chrome/Edge 에서 추가 빌드 없이 렌더되어야 함.

### 10.2 데이터 · 보안
- **사내 영업포탈의 샘플 코드/이미지를 반입하지 않는다.** 외부 공개 샘플 기준으로 아키텍처를 잡는다.
- PMS 소스 활용 안은 취소됨. 대체 방안 재검토 중(§12 OI-5).
- 사내 UI 표준 카탈로그는 PoC 용 최소 범위만 별도 정리해 사용.
- 입력 이미지·프롬프트에 사내 기밀/개인정보가 포함되지 않도록 UI 에 가이드 문구 표시.
- API 키는 소스에 하드코딩하지 않는다. 입력·산출물은 로컬/PoC 환경 내에서만 취급.
- 상용 API 전송 데이터의 범위·보관 정책을 사전 확인 (§12 OI-6).

### 10.3 가정
- 대상 화면 3종의 참조 이미지·기대 결과가 확보된다.
- 사내 UI 표준 최소 세트를 PoC 기간 내 정의 가능하다.
- LLM API 사용 한도/비용이 PoC 수행에 충분하다.

## 11. 수락 기준 (Acceptance Criteria)

구현이 끝났다고 보려면 아래를 모두 만족해야 한다.

| # | 기준 |
|---|---|
| AC-1 | `npm install && npm run dev` 만으로 로컬 구동되고 웹 UI 가 뜬다. |
| AC-2 | 자연어 입력만으로 대상 화면 3종 각각에 대해 스키마를 통과하는 IR 이 생성된다. |
| AC-3 | 3종 모두 `static-html` 타겟에서 Preview 가 렌더되고, 다운로드한 `screen.html` 이 단독으로 열린다. |
| AC-4 | 생성 소스가 사내 표준 `componentKey`/`tokenKey` 를 사용하며, 미사용 시 `report.json` 에 fallback 사유가 남는다. |
| AC-5 | 동일 입력 3회 반복 시 표준 컴포넌트/토큰 사용 구조가 정성 평가에서 크게 흔들리지 않는다. |
| AC-6 | Stage B 자동 수정 루프가 최대 3회로 제한되고, 실패 시 오류 로그가 사용자에게 노출된다. |
| AC-7 | Stage A 질문에 답하면 반영된 IR 로 재생성된다. |
| AC-8 | 생성 1건마다 `runs/<timestamp>/` 에 input·ir·output·report 가 저장된다. |
| AC-9 | API 키가 프론트엔드 번들·응답·로그에 노출되지 않는다. |
| AC-10 | `react-vite-ts` 타겟이 최소 1개 화면에서 동작한다. |
| AC-11 | 단일 화면 생성(입력 제출 → Preview)이 통상 3분 이내(재시도 포함). |
| AC-12 | 대상 화면 3종 실행 결과와 위 기준 충족 여부가 `docs/03_평가결과.md` 에 정리된다. |
