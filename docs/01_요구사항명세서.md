## 1. 개요

### 1.1 목적
본 문서는 "AI Screen Draft" PoC의 개발 착수를 위해 핵심 범위, 기능/비기능 요구사항, 외부 인터페이스, 제약사항, 성공 기준을 정의한다. 1개월 내에 개발 가능한 최소 범위를 명확히 하고, 이후 정식 개발 전환 여부를 판단하는 근거를 제공한다.

### 1.2 배경
- 화면(UI) 초안 작성은 현재 수작업 위주로 시간이 많이 소요되고, 작성자마다 사내 UI 스타일 적용 편차가 발생한다.
- 상용 LLM의 멀티모달·코드 생성 역량을 활용해 "자연어/스케치 입력 → 사내 UI 표준 기반 화면 초안 + HTML 소스"를 자동 생성하는 접근의 실효성을 검증한다.

### 1.3 PoC 목표
1. 자연어 입력 → 사내 UI 표준 기반 화면 초안 생성
2. 생성 화면 Preview 제공
3. HTML 소스 확인 및 활용(복사/다운로드)

### 1.4 PoC 성공 기준
| # | 기준 | 측정 방법(안) |
|---|---|---|
| SC-1 | 실제 사용할 만한 화면 초안이 생성되는가 | 평가자 체크리스트 기반 정성 평가(레이아웃 타당성, 컴포넌트 적합성) |
| SC-2 | 사내 UI 스타일이 일정하게 반영되는가 | 동일 입력 반복 생성 시 표준 컴포넌트/토큰 사용 일관성 비율 |
| SC-3 | 기존 방식보다 화면 초안 작성 시간이 줄어드는가 | 동일 화면 N건에 대해 수작업 소요시간 vs 도구 사용 소요시간 비교 |

### 1.5 용어 정의
| 용어 | 설명 |
|---|---|
| IR (Intermediate Representation) | Stage A가 출력하는 화면 구조 중간 표현. 레이아웃/컴포넌트/텍스트/확신도를 담은 JSON |
| Stage A | 스케치·이미지·자연어를 분석해 IR을 생성하는 단계(멀티모달 LLM) |
| Stage B | IR + 사내 UI 표준을 입력받아 프론트엔드 코드를 생성하는 단계(코드 생성 LLM) |
| 사내 UI 표준 | 사내 컴포넌트 카탈로그, 디자인 토큰, 레이아웃 가이드의 총칭 |
| componentKey / tokenKey | 사내 표준 컴포넌트/토큰을 식별하는 키 |
| 화면 초안(Draft) | 최종 산출물이 아닌, 기획·검토용으로 생성된 화면과 그 소스 |

## 2. 전체 시스템 개요

### 2.1 처리 흐름 (2단계 파이프라인)

```
[사용자 입력]                  [Stage A: 구조 분석]           [사내 UI 표준]
 - 자연어 프롬프트     ──▶      멀티모달 LLM        ──▶  IR(JSON)  +  컴포넌트 카탈로그/토큰
 - 스케치/화이트보드 사진        · 레이아웃 계층 추론                     │
 - 화면 스크린샷                · 컴포넌트 타입/배치 추론                 ▼
                               · 텍스트(라벨/컬럼) 인식        [Stage B: 코드 생성]
                               · 확신도/미확정 요소 표기         코드 생성 LLM
                                                                · 표준 컴포넌트 우선 매핑
                                                                · 레이아웃/스타일 구현
                                                                · 더미 데이터/핸들러 stub
                                                                        │
                                                                        ▼
                                                            [산출물]
                                                             - 화면 Preview(렌더링)
                                                             - HTML/프론트엔드 소스
                                                             - IR(JSON), 미확정 항목 리스트
```

### 2.2 단계 분리 이유
- **Stage A(구조 분석)**: 이미지 이해, 레이아웃/컴포넌트 추론, 누락·불명확 요소 처리(확신도 표기, 질문 생성)가 핵심 역량.
- **Stage B(코드 생성)**: 컴포넌트 구조화, 스타일/레이아웃 구현, 사내 UI 표준 준수, 빌드/타입 오류 없는 코드 출력이 핵심 역량.
- IR을 JSON Schema로 고정하여 모델 교체·테스트·품질 비교를 용이하게 한다.

### 2.3 LLM 채택 (잠정)
| 단계 | 모델(잠정) | 사유 | 확정 여부 |
|---|---|---|---|
| Stage A | GPT 계열 (멀티모달) | 이미지 이해·레이아웃 추론 | **미확정** — 후보 비교 필요 |
| Stage B | Claude 계열 | 구조화된 프론트엔드 코드 생성 | **미확정** — 후보 비교 필요 |

> 회의 TODO "프로젝트 LLM 채택 (GPT / 클로드, 더 찾아보기)"에 따라 PoC 초기에 동일 입력셋으로 A/B 비교 후 확정한다. 상용 API 사용을 전제로 한다.

## 3. 범위 (Scope)

### 3.1 PoC 포함 (In Scope)
- 자연어 프롬프트 입력을 통한 단일 화면 초안 생성
- (가능 시) 스케치/스크린샷 이미지 입력 지원
- Stage A → IR(JSON) 생성 및 확인
- 사내 UI 표준 컴포넌트/토큰 매핑 (PoC용 축소 카탈로그 기준)
- Stage B → HTML 기반 프론트엔드 소스 생성
- 생성 화면 Preview(브라우저 렌더링)
- HTML/소스 확인, 복사, 다운로드
- 미확정 요소 표기 및 사용자 확인(질문-응답) 후 재생성
- Stage B 오류(타입/빌드/레이아웃) 자동 재시도 루프 (제한 횟수)

### 3.2 PoC 제외 (Out of Scope)
- 프로덕션 수준의 완전한 소스코드(라우팅, 전역 상태관리, 실제 API 연동)
- 실제 백엔드/데이터 연동 (더미 데이터·핸들러 stub로 대체)
- 다중 화면/플로우 자동 생성, 화면 간 인터랙션
- 디자인 편집기(드래그앤드롭 캔버스) 제공
- 사내 전체 컴포넌트 카탈로그 완전 커버리지
- 사용자 인증/권한 관리, 다중 사용자 협업
- 영업포탈 등 사내 시스템으로의 배포/통합
- 접근성·반응형의 전수 검증(기본 가드레일 수준만 적용)

## 4. 기능 요구사항 (Functional Requirements)

우선순위: **M**(Must, PoC 필수) / **S**(Should, 가능 시) / **C**(Could, 여유 시)

### FR-1. 입력 수집
| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-1.1 | 사용자는 자연어 텍스트로 원하는 화면을 설명하여 입력할 수 있다. | M |
| FR-1.2 | 사용자는 스케치/화이트보드 사진 또는 화면 스크린샷 이미지를 업로드하여 입력할 수 있다. | S |
| FR-1.3 | 텍스트와 이미지를 동시에 입력할 수 있다(이미지 기준 + 텍스트 보정). | S |
| FR-1.4 | 지원 이미지 형식(PNG/JPG)과 최대 용량·해상도 제한을 안내한다. | M |
| FR-1.5 | 대상 화면 유형(예: 팝업 / 모니터링 전체조회 / 메인화면)을 선택하거나 프리셋으로 지정할 수 있다. | S |

### FR-2. Stage A — 화면 구조 분석 (IR 생성)
| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-2.1 | 입력을 분석하여 고정된 JSON Schema를 따르는 IR을 생성한다. | M |
| FR-2.2 | IR은 레이아웃 계층(섹션/그리드/컨테이너)을 표현한다. | M |
| FR-2.3 | IR은 컴포넌트 타입(button/input/table/card/select 등), 계층, 상대적 정렬·배치를 표현한다. | M |
| FR-2.4 | IR은 텍스트 요소(라벨/플레이스홀더/표 컬럼명)를 포함한다. | M |
| FR-2.5 | 불명확·누락 요소는 확신도(confidence)와 함께 표기하고, 후보안 또는 사용자 질문으로 분리한다. | M |
| FR-2.6 | IR의 각 컴포넌트는 사내 UI 표준 매핑을 위한 키(componentKey 등) 슬롯을 가진다. | M |
| FR-2.7 | 이미지 품질 문제(흐림/잘림/저해상도) 감지 시 재촬영·전처리 가이드를 제시한다. | S |

### FR-3. 사내 UI 표준 매핑
| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-3.1 | PoC용 사내 UI 표준 카탈로그(컴포넌트 목록 + 토큰 + 레이아웃 가이드)를 시스템에 등록·관리한다. | M |
| FR-3.2 | IR의 각 컴포넌트를 표준 컴포넌트(componentKey)로 매핑한다. | M |
| FR-3.3 | 표준에 없는 컴포넌트는 정의된 fallback 규칙에 따라 대체하고, 대체 사실을 표기한다. | M |
| FR-3.4 | 색상/간격/타이포 등은 사내 디자인 토큰(tokenKey)으로 치환한다. | M |
| FR-3.5 | 허용/금지 컴포넌트 정책을 설정할 수 있고, 금지 컴포넌트는 생성 결과에서 배제한다. | S |

### FR-4. Stage B — UI 코드 생성
| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-4.1 | IR + 사내 UI 표준 + 타겟 스택을 입력받아 프론트엔드 소스를 생성한다. | M |
| FR-4.2 | 산출물은 브라우저에서 바로 렌더링 가능한 HTML(및 필요한 CSS)을 포함한다. | M |
| FR-4.3 | 사내 표준 컴포넌트를 우선 사용하고, 토큰 기반 스타일을 적용한다. | M |
| FR-4.4 | 동작 로직은 범위를 제한한다(더미 데이터, 핸들러 stub). 실제 API 연동은 하지 않는다. | M |
| FR-4.5 | 기본 접근성 속성(aria/label)과 기본 반응형 규칙, lint/format 규약을 준수한다. | S |
| FR-4.6 | 필요 시 보조 파일(CSS/토큰/상수)을 함께 생성한다. | S |
| FR-4.7 | 타겟 스택은 설정으로 지정한다(기본값: 정적 HTML + CSS. 옵션: React/Next + 스타일링 방식). | S |

|---|---|---|

| FR-6.2 | 소스를 클립보드로 복사하거나 파일로 다운로드할 수 있다. | M |

## 5. 제약사항 및 가정

### 5.1 기술 제약
- 상용 LLM API를 사용한다(자체 모델 학습·호스팅 없음).
- Stage A 출력(IR)은 JSON Schema로 고정한다.
- PoC 산출물의 기본 타겟은 정적 HTML + CSS이며, 프레임워크 코드는 옵션이다.

### 5.2 데이터·보안 제약 (팀장 의견 반영)
- **샘플 코드/이미지를 사내 영업포탈에서 반입하지 않는다.** 외부에 공개되는 샘플 소스를 기준으로 아키텍처를 잡고 진행한다.
- PMS 소스 활용 안은 취소되었으며, 대체 방안은 재검토 중이다.
- 사내 UI 표준 카탈로그는 PoC용으로 최소 범위만 별도 정리하여 사용한다.
- 입력 이미지·프롬프트에 사내 기밀/개인정보가 포함되지 않도록 사용자 가이드를 제공한다.
- 상용 API로 전송되는 데이터의 범위·보관 정책을 사전 확인한다. *(확인 필요 항목)*

### 5.3 가정
- PoC 평가에 사용할 대상 화면 3종의 참조 이미지 및 기대 결과가 확보된다.
- 사내 UI 표준(컴포넌트/토큰) 최소 세트를 PoC 기간 내 정의 가능하다.
- LLM API 사용 한도/비용이 PoC 수행에 충분하다.

## 6. 외부 인터페이스 요구사항

### 6.1 LLM API 인터페이스
| 항목 | 내용 |
|---|---|
| Stage A | 멀티모달 입력(텍스트+이미지) → 구조화 JSON 출력. JSON Schema/응답 포맷 강제 옵션 사용 |
| Stage B | 텍스트 입력(IR + 표준 + 정책) → 코드 출력 |
| 공통 | API 키 관리(환경변수/시크릿), 타임아웃·재시도·오류 처리, 토큰/비용 로깅 |

### 6.2 사내 UI 표준 카탈로그 인터페이스
- 컴포넌트 카탈로그: `componentKey`, 표시명, 파라미터/슬롯, 사용 예시(HTML snippet)
- 디자인 토큰: `tokenKey`, 값(색상/간격/타이포/라운드 등)
- 레이아웃 가이드: 그리드 규칙, 간격 스케일, 화면 유형별 템플릿

### 6.3 IR 데이터 포맷 (개요, 상세는 별도 스키마 문서)
```jsonc
{
  "screen": { "type": "popup | monitoring-list | main | custom", "title": "..." },
  "layout": [
    {
      "id": "sec-1",
      "kind": "section | grid | container",
      "children": ["cmp-1", "cmp-2"],
      "props": { "columns": 12, "gap": "md" }
    }
  ],
  "components": [
    {
      "id": "cmp-1",
      "type": "button | input | table | card | select | text | ...",
      "parentId": "sec-1",
      "position": { "order": 1, "align": "left" },
      "text": { "label": "조회", "placeholder": null },
      "componentKey": null,          // 사내 표준 매핑 결과 (Stage A는 후보/null, 매핑 단계에서 확정)
      "tokenKeys": [],
      "confidence": 0.82,
      "uncertain": false
    }
  ],
  "questions": [
    { "targetId": "cmp-3", "question": "이 영역은 그리드입니까, 카드 리스트입니까?", "options": ["grid", "card-list"] }
  ]
}
```

### 6.4 산출물 포맷
- `screen.html` (+ `styles.css` / `tokens.css` 필요 시)
- `ir.json`
- `report.json` (재시도 횟수, 처리 시간, 미확정 항목, fallback 적용 목록)

## 7. 비기능 요구사항 (Non-Functional Requirements)

| 분류 | ID | 요구사항 |
|---|---|---|
| 성능 | NFR-1 | 단일 화면 생성(입력 제출 → Preview 표시)까지 통상 3분 이내(재시도 포함) 목표. |
| 성능 | NFR-2 | Stage B 자동 수정 루프는 최대 N회(기본 3회)로 제한하여 무한 반복을 방지한다. |
| 일관성 | NFR-3 | 동일 입력 3회 반복 시 표준 컴포넌트/토큰 사용의 구조적 일관성을 정성 평가에서 확보한다(SC-2). |
| 사용성 | NFR-4 | 비개발자(기획/PM)도 입력~Preview~소스 확인까지 가이드 없이 수행 가능해야 한다. |
| 신뢰성 | NFR-5 | LLM/네트워크 오류 시 사용자에게 명확한 메시지와 재시도 수단을 제공한다. |
| 보안 | NFR-6 | API 키는 소스에 하드코딩하지 않는다. 입력·산출물은 로컬/PoC 환경 내에서만 취급한다. |
| 이식성 | NFR-7 | 생성 HTML은 최신 Chrome/Edge에서 추가 빌드 없이 렌더링되어야 한다. |
| 유지보수 | NFR-8 | Stage A/B 프롬프트, IR 스키마, 표준 카탈로그는 코드와 분리하여 파일로 관리한다. |
| 관측성 | NFR-9 | 세션별 입력/IR/출력/지표를 파일로 남겨 평가에 활용한다. |
